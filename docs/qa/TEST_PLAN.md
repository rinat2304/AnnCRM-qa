# Test Plan — AnnCRM

## 1. Общая информация

**Проект:** AnnCRM
**Тип тестирования:** функциональное, API, интеграционное, негативное
**Инструменты:** Python, pytest, requests
**Среда:** локальная / CI GitHub Actions
**API:** REST API
**База данных:** PostgreSQL

---

## 2. Цель тестирования

Цель тестирования — проверить корректность работы основных API-эндпоинтов приложения AnnCRM, связанных с:

* регистрацией пользователей;
* авторизацией пользователей;
* выдачей JWT-токенов;
* проверкой авторизации;
* работой с клиентами;
* разграничением доступа между пользователями;
* обработкой некорректных запросов;
* обработкой отсутствующих ресурсов;
* корректной работой API в CI-окружении.

---

## 3. Область тестирования

### 3.1 Authentication API

Проверяются следующие сценарии:

* успешная авторизация пользователя;
* авторизация с неверным паролем;
* запрос защищённого ресурса с валидным токеном;
* запрос защищённого ресурса без токена;
* запрос с невалидным токеном.

### 3.2 Clients API

Проверяются:

* получение списка клиентов;
* создание клиента;
* получение клиента по ID;
* изменение клиента;
* удаление клиента;
* запрос несуществующего клиента;
* удаление несуществующего клиента;
* создание клиента без обязательного поля;
* доступ пользователя только к собственным клиентам;
* запрет изменения чужого клиента;
* запрет удаления чужого клиента.

---

## 4. Виды тестирования

### 4.1 Позитивное тестирование

Проверяется корректная работа API при передаче валидных данных.

Примеры:

* корректные данные авторизации;
* создание клиента с валидными параметрами;
* получение существующего клиента;
* изменение существующего клиента;
* удаление собственного клиента.

### 4.2 Негативное тестирование

Проверяется корректная обработка ошибочных запросов.

Примеры:

* неверный пароль;
* отсутствие токена;
* невалидный токен;
* несуществующий ID;
* отсутствие обязательного поля;
* попытка получить или изменить чужой ресурс.

### 4.3 Интеграционное тестирование

Проверяется взаимодействие:

* API и PostgreSQL;
* авторизации и JWT;
* пользователей и клиентов;
* миграций базы данных и приложения.

### 4.4 Регрессионное тестирование

После изменений в backend проверяется, что существующая функциональность продолжает работать.

---

## 5. Тестовая среда

### Локальная среда

* ОС: Windows
* Python: 3.12
* pytest
* requests
* PostgreSQL
* Backend AnnCRM

### CI

Тесты запускаются в GitHub Actions:

* ОС: Ubuntu
* Python: 3.12
* PostgreSQL 16
* отдельная тестовая база данных;
* backend запускается через Uvicorn;
* перед тестами выполняются Alembic migrations.

---

## 6. Тестовые данные

Для тестирования используются два изолированных тестовых пользователя.

### Пользователь 1

```text
Основные сценарии авторизации и работы с клиентами
```

### Пользователь 2

```text
Проверка разграничения доступа 
```

Тестовые credentials передаются через environment variables и создаются
автоматически перед выполнением API-тестов.

## 8. Критерии входа

Тестирование начинается при выполнении следующих условий:

* backend доступен;
* PostgreSQL запущен;
* база данных создана;
* миграции применены;
* API отвечает на HTTP-запросы;
* тестовые пользователи существуют;
* установлены необходимые Python-зависимости.

---

## 9. Критерии выхода

Тестирование считается успешно завершённым, если:

* все запланированные тесты выполнены;
* критические дефекты отсутствуют;
* авторизация работает корректно;
* защищённые endpoints требуют авторизацию;
* пользователи не имеют доступа к чужим ресурсам;
* CRUD-операции с клиентами работают корректно;
* негативные сценарии возвращают ожидаемые HTTP-коды;
* API-тесты успешно проходят локально;
* API-тесты успешно проходят в CI.

---

## 10. Автоматизация

Автоматизированные тесты запускаются командой:

```bash
pytest tests/api -v
```

Ожидаемый результат:

```text
16 passed
```

---

## 11. CI/CD

Для автоматического запуска тестов используется GitHub Actions.

Pipeline выполняет следующие действия:

1. Получает QA-репозиторий.
2. Устанавливает Python.
3. Устанавливает зависимости QA.
4. Получает backend-репозиторий.
5. Устанавливает зависимости backend.
6. Запускает PostgreSQL.
7. Выполняет миграции базы данных.
8. Запускает backend.
9. Создаёт тестовых пользователей.
10. Запускает API-тесты.
11. Завершает workflow с успешным или ошибочным статусом.

---

## 12. Риски

Основные риски:

* несоответствие тестовых данных данным backend;
* отсутствие тестовых пользователей;
* неправильная конфигурация `DATABASE_URL`;
* несовпадение `SECRET_KEY`;
* проблемы с миграциями;
* backend может не успеть запуститься до начала тестов;
* различия между локальной и CI-средой;
* изменения API без обновления автотестов.

---

## 13. Обработка дефектов

При обнаружении дефекта необходимо зафиксировать:

* название дефекта;
* endpoint;
* HTTP-метод;
* входные данные;
* ожидаемый результат;
* фактический результат;
* HTTP status code;
* response body;
* шаги воспроизведения;
* окружение;
* commit/version;
* логи при наличии.

---

## 14. Приоритеты дефектов

### Critical

Полностью блокирует работу API или основную функциональность.

Пример:

* невозможно авторизоваться ни одному пользователю;
* API полностью недоступен;
* критическая проблема с безопасностью.

### High

Серьёзно нарушает основную функциональность.

Пример:

* пользователь получает доступ к данным другого пользователя;
* невозможно создать или удалить клиента.

### Medium

Функциональность работает некорректно, но существует обходной путь.

### Low

Незначительный дефект, не влияющий на основную функциональность.

---

## 15. Результаты тестирования

Результаты каждого запуска фиксируются отдельно.

Пример:

```text
16 passed
```

При наличии ошибок необходимо указать:

```text
X passed
Y failed
Z errors
```

и приложить traceback и описание причины.

---

## 16. Итоговая оценка

API считается готовым к следующему этапу тестирования, если:

* все критические сценарии проходят;
* авторизация работает корректно;
* проверка прав доступа работает корректно;
* CRUD клиентов работает корректно;
* негативные сценарии обрабатываются корректно;
* локальные тесты проходят;
* CI-тесты проходят без ошибок.

---

## 17. Ответственные

**QA:** разработка и поддержка тест-кейсов, проведение тестирования, анализ результатов.

**Backend:** исправление дефектов API и серверной логики.

**CI/CD:** автоматический запуск тестов и контроль результатов pipeline.
